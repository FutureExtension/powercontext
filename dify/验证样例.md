## 2. 样例 A —— 接案检索（读路径）

### 2.1 操作顺序

1. 打开 Dify 应用《雾隐镇 · 夜班档案室》→ 点「运行」。
2. 顶部表单：
   - **侦探代号** = `detective_001`（默认）
   - **接手案件** = `CASE-2403`（默认，即"雾钟停摆的那一夜"）
3. 在对话框里输入第一句：

   > **钟楼的雾钟到底是怎么坏的？铜锤又是谁的？**

4. 等阿灯回答。
5. 打开 Dify 的**日志 / 节点执行记录**，点开「检索卷宗·物证·镇志」节点，看它的输出 JSON。

### 2.2 预期交互 / 输出形式

- 阿灯以角色口吻回答，**只用卷宗里的内容**，并且用 `【EV-xxxx】` / `【SUS-xx】` 标注引用的物证与镇民。
- 应当提到 CASE-2403 的关键物证，例如「断掉的钟舌销」【EV-0301】、「钟楼下的铜屑」【EV-0302】、「海雾预警的空档」【EV-0305】，
  并提到砚师傅温砚【SUS-05】。
- 因为上一轮已经排除了丁叔，**回答里不应把老丁当成主要嫌疑人**。
- 回复末尾有一段「—— 阿灯在档案室的记录 ——」，说明这一轮往 seekdb 写了多少行。

**（b）`/search_archive` 实际执行的 SQL（节选，原样出自工具返回的 `sql_trace`）**

```sql
-- 取语料（用来反查检索词）
SELECT CONCAT_WS(' ', title, keywords, summary) AS t FROM case_files
SELECT CONCAT_WS(' ', name, keywords, detail)  AS t FROM evidence
SELECT CONCAT_WS(' ', name, alias, occupation, motive) AS t FROM suspects
SELECT CONCAT_WS(' ', topic, content, keywords) AS t FROM town_lore
-- 取词典（地点 / 人名）
SELECT DISTINCT location FROM case_files UNION SELECT DISTINCT location FROM evidence
SELECT name FROM suspects UNION SELECT alias FROM suspects
-- 卷宗检索：结构化过滤 + 关键词条件
SELECT case_id, title, crime_type, location, occurred_at, severity, keywords, summary, status
FROM case_files
WHERE (case_id = %s OR %s = '')
  AND (location = %s OR %s = '')
  AND status <> 'closed'
  AND (CONCAT_WS(' ', title, keywords, summary) LIKE %s OR ...)
ORDER BY severity DESC, occurred_at DESC LIMIT %s
-- 物证检索
SELECT evidence_id, case_id, name, detail, location, found_at, keywords, weight
FROM evidence
WHERE (case_id = %s OR %s = '')
  AND (CONCAT_WS(' ', name, keywords, detail) LIKE %s OR ...)
ORDER BY weight DESC, found_at ASC LIMIT %s
-- 镇民检索
SELECT suspect_id, name, alias, occupation, motive, hideout, alibi, note
FROM suspects
WHERE (CONCAT_WS(' ', name, alias, occupation, motive, hideout) LIKE %s OR ...)
LIMIT %s
-- 镇志检索
SELECT lore_id, topic, content, keywords FROM town_lore
WHERE (CONCAT_WS(' ', topic, content, keywords) LIKE %s OR ...) LIMIT %s
```

**（c）反查检索词的效果**（这一步是"自然语言 → 数据库检索"的关键）

`extract_terms()` 把「钟楼的雾钟到底是怎么坏的？铜锤又是谁的？」切成 2/3/4-gram，
**只保留在 seekdb 语料里真实出现过的字串**，于是留下的会是像
`钟楼`、`雾钟`、`铜锤`、`雾钟到底`… 这样的词；
而像`到底`、`是谁`这种库里没有的词会被丢掉。地点与人名则是直接从
`case_files.location` / `suspects.name` 命中的。

## 3. 样例 B —— 跨会话记忆（读 `player_progress`）

### 3.1 操作顺序

1. **新开一个会话**（Dify 右上角「新建会话」/ 清空对话）。
2. 表单仍填 `detective_001` / `CASE-2403`。
3. 输入：

   > **我上次查到哪儿了？老丁还有嫌疑吗？**

4. 看阿灯的回答，并点开「读取调查进度」节点看输出。

### 3.2 预期交互 / 输出形式

阿灯应当**明确说出上一轮的进展**，例如：
"上一轮你把【EV-0302】钟楼下的铜屑记下来了，也已经把【SUS-08】丁叔排除掉了——他那晚确实在钟楼附近转悠，但没碰过钟。
铜屑这条线你还没查清是谁留下的。"

### 3.3 实际运行结果

**HTTP 层的真实返回**（`smoke_test.py --offline` 中对应断言已 PASS）：

```json
{
  "ok": true,
  "player_id": "detective_001",
  "case_id": "CASE-2403",
  "found": true,
  "progress": {
    "player_id": "detective_001",
    "case_id": "CASE-2403",
    "cleared_evidence": ["EV-0302"],
    "eliminated_suspects": ["SUS-08"],
    "notes": "上一夜已排除丁叔（老丁）：他那晚确实在钟楼附近转悠，但没碰过钟。",
    "turns": 2
  },
  "log_count": 2
}
```

对应的真实 SQL：

```sql
SELECT player_id, case_id, cleared_evidence, eliminated_suspects, notes, turns, updated_at
FROM player_progress WHERE player_id = %s AND case_id = %s

SELECT log_id, case_id, action, question, reply, evidence_ids, suspect_ids, created_at
FROM investigation_log WHERE player_id = %s AND case_id = %s ORDER BY log_id DESC LIMIT 5

SELECT COUNT(*) AS c FROM investigation_log WHERE player_id = %s
```

> **为什么这条能证明"记忆真的在数据库里"**：Dify 的会话记忆存在它自己的库里，
> 换一个会话就没了。这里换一个会话后仍能读出上一轮的 `cleared_evidence` / `eliminated_suspects`，
> 只可能来自 seekdb 的 `player_progress` 表。

## 4. 样例 C —— 结案写回（写路径）

### 4.1 操作顺序

1. 接着样例 A/B 的会话（不用换会话）。
2. 输入一句能把关键物证一次问全的话，例如：

   > **钟楼那边把钟舌销、铜屑、雾钟预警的记录都给我翻出来**

3. 阿灯回答后（应当一次给出 ≥2 条 `weight>=2` 的物证）。
4. 再输入：

   > **结案**

5. 看阿灯的结案陈词，以及回复末尾的「—— 阿灯在档案室的记录 ——」。

### 4.2 预期交互 / 输出形式

- 走**结案分支**（「可以结案吗」→ true → 写回·结案 → 组装结案报告）。
- 末尾的记录应类似：

  ```text
  —— 阿灯在档案室的记录 ——
  - 采纳的关键物证：EV-0301,EV-0302
  - 结案对象：SUS-05
  - 仍未排除的镇民：SUS-05
  - 已写入 seekdb：player_progress 1 行、investigation_log 1 行、case_files 1 行
  - 案卷状态：closed（这一条也写回了 seekdb 的 case_files 表）
  - 你的调查进度存在 seekdb 的 player_progress 表里，下次开新会话阿灯还记得。
  ```

### 4.3 实际运行结果与落库证据

**真实写入的 SQL**（`smoke_test.py` 真实模式会把它们打印出来）：

```sql
-- 1) 合并后 UPSERT 进度
INSERT INTO player_progress
  (player_id, case_id, cleared_evidence, eliminated_suspects, notes, turns, updated_at)
VALUES (%s, %s, %s, %s, %s, %s, NOW())
ON DUPLICATE KEY UPDATE cleared_evidence = VALUES(cleared_evidence),
  eliminated_suspects = VALUES(eliminated_suspects), notes = VALUES(notes),
  turns = VALUES(turns), updated_at = NOW()

-- 2) 记录这一轮问答
INSERT INTO investigation_log
  (player_id, case_id, action, question, reply, evidence_ids, suspect_ids, created_at)
VALUES (%s, %s, %s, %s, %s, %s, %s, NOW())

-- 3) 结案：改卷宗状态
UPDATE case_files SET status = 'closed', closed_at = NOW(), closed_by = %s WHERE case_id = %s
```

**复核方式（直连 seekdb）**：

```sql
SELECT log_id, player_id, case_id, action, question, created_at
FROM investigation_log WHERE player_id = 'smoke_tester' ORDER BY log_id;

SELECT player_id, case_id, cleared_evidence, eliminated_suspects, turns, updated_at
FROM player_progress WHERE player_id = 'smoke_tester';

SELECT case_id, status, closed_at, closed_by FROM case_files WHERE case_id = 'CASE-2403';
```

`smoke_test.py` 的真实模式会**自动跑完这三步并直连数据库复核**，
输出形如（真实 seekdb 运行时）：

```text
[PASS] seekdb.investigation_log 里能查到冒烟测试的记录 -> 2 行
   log_id=1 action=note question=钟楼的雾钟到底是怎么坏的？铜锤又是谁的？
   log_id=2 action=close question=结案
[PASS] seekdb.player_progress 里能查到冒烟测试的进度 -> 1 行
   cleared_evidence=["EV-0301", "EV-0302"] turns=2 updated_at=2026-11-05 15:00:00
[PASS] seekdb.case_files 能查到该案件 -> 1 行
   status=closed
   已把 CASE-2403 的 status 复原为 open（冒烟测试不污染初始数据）
```

> 上面的 `updated_at` / `log_id` 是**示意格式**（说明每列的含义）；
> 真实数值由运行时的 seekdb 产生。上面 `[PASS]` 行是脚本实际会打印的格式。

## 6. API 调用样例（可选入口）

Dify 应用也可以用 API 驱动：

```bash
curl -X POST 'http://<你的Dify地址>/v1/chat-messages' \
  -H 'Authorization: Bearer <app-api-key>' \
  -H 'Content-Type: application/json' \
  -d '{
    "inputs": { "player_id": "detective_001", "case_id": "CASE-2403" },
    "query": "钟楼的雾钟到底是怎么坏的？铜锤又是谁的？",

    "user": "detective_001"

但 `player_id` 不变的话，进度依然共享——这一点在 README 的已知限制里也写了。

## 7. seekdb 发挥作用的记录汇总

| 核对项 | 证据形式 |
|--------|---------|
| 连接的是 seekdb 而不是别的库 | `GET /health` 返回 `"seekdb": {"ok": true, "version": "...seekdb...", "database": "wuyin_archive"}` |
| 用的确实是 MySQL 协议 | `service/app.py` 里 `pymysql.connect(host=..., port=2881, ...)`；网络层是标准 MySQL 握手 |

| 读：记忆表 | `sql_trace` 里的 `SELECT ... FROM player_progress / investigation_log` |
| 写：进度 UPSERT | `sql_trace` 里的 `INSERT INTO player_progress ... ON DUPLICATE KEY UPDATE ...` |
| 写：日志 INSERT | `sql_trace` 里的 `INSERT INTO investigation_log ...` |
| 写：结案 UPDATE | `sql_trace` 里的 `UPDATE case_files SET status = 'closed' ...` |
| 行真的落库 | 直连 seekdb 的 `SELECT`（`smoke_test.py` 自动做） |
| 全文索引是否生效 | `/health` 的 `fulltext_enabled` + 每次检索的 `strategy`（`fulltext+like` / `like`） |
| 降级能力 | 删掉 FULLTEXT 索引后重启服务，`strategy` 变 `like`，检索与写回全部照常 |
| 部署形态 | README `6.1（Docker / 官方安装包），端口 2881，数据库 `wuyin_archive` |

为保证评审可复现，`service/smoke_test.py` 提供了**离线 mock 模式**，
在没有数据库的机器上也能验证 HTTP 契约、编排逻辑与写回语义（`2.3(a) 就是它的真实输出）。

## 9. 如何恢复初始状态（便于重复验证）

样例 C 会真的改 `case_files.status` 并写进度/日志。恢复方式：

**方式 A（推荐）**：```bash
cd dify/service
python smoke_test.py --reset
```
它会删掉 `smoke_tester` 的 `player_progress` / `investigation_log` 行，
并把被测试关掉的卷宗恢复成 `status='open'`。

**方式 B**：重灌初始数据（`init_data.sql` 已做成**幂等**，可反复执行）
```bash
python smoke_test.py --init
```
脚本开头会先 `DELETE` 掉固定编号的演示数据再 `INSERT`，所以重复执行不会产生重复行。
若想彻底重来：
```sql
DROP DATABASE IF EXISTS wuyin_archive;
```
再执行一次 `init_data.sql` 即可。

**方式 C**：只恢复玩家进度（不影响别人）
```sql
DELETE FROM investigation_log WHERE player_id = 'detective_001';
DELETE FROM player_progress    WHERE player_id = 'detective_001';
UPDATE case_files SET status = 'open', closed_at = NULL, closed_by = NULL
WHERE case_id = 'CASE-2403';
```

> 评审如果只想体验、不想动初始数据，用**别的侦探代号**即可（例如 `detective_test_2`）：
> `player_progress` 与 `investigation_log` 都按 `player_id` 关联，互不干扰。
