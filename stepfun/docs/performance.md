## 3. 批大小扫描（batch size sweep）

数据来源：`data/bench.json` → `batchSweep`。
方法：**同一个 embedder 实例**，只改变每次送入模型的批大小；先预热一次排除首次懒初始化；每个 batch 重复 5 次取中位数；语料固定为同一批 36 块。

| batchSize | 文档向量化中位数 (ms) | 吞吐 (块/秒) | 5 次原始样本 (ms) |
|---|---|---|---|
| 1 | **2,614.09** | **13.77** | 2614.09, 2739.59, 2664.94, 2491.51, 2535.95 |
| 4 | 2,948.51 | 12.21 | 2948.51, 2560.74, 3118.58, 2665.09, 3137.26 |
| 8 | 3,645.32 | 9.88 | 3004.31, 4058.94, 3645.32, 5624.86, 3515.28 |
| 16 | **2,659.39** | **13.54** | 3426.47, 2428.08, 3023.75, 2602.25, 2659.39 |
| 32 | 3,033.03 | 11.87 | 2985.59, 3317.83, 3033.03, 2967.55, 4030.60 |
| 64 | 2,832.09 | 12.71 | 3650.07, 4781.05, 2832.09, 2740.35, 2568.60 |

### 结论（与直觉相反，如实给出）

* 在这台 **3 核 / 1.60 GHz** 的 CPU 上，**加大 batch 没有带来吞吐提升**：全部 6 个点的吞吐都落在 **9.88 ~ 13.77 块/秒**区间内，batch=1（13.77）与 batch=16（13.54）实际持平，差异处于样本噪声范围（单个 batch=8 的样本就出现了 5624.86 ms 的抖动）。
* 原因：bge-small-zh-v1.5 的中文序列长度达到 **512 token**，batch=16 意味着单次前向要处理 8192 个 token，在 3 核小内存的机器上是**内存带宽瓶颈**，而不是矩阵乘调度瓶颈。
* 因此前端默认 batch 设为 16（`public/index.html` 的 `#in-batch`），在导入场景兼顾吞吐与首字节延迟；用户可按自己的机器调整。
* **未测**：浏览器端 WASM 多线程与 WebGPU 后端的 batch 扫描（原因见 §1）。

## 4. 量化前后对比（fp32 基线 / fp16 / int8）

数据来源：`data/bench.json` → `comparison`。同一语料、同一查询集、同一 Top-K=5、同一 batch=16、同一机器。

| 配置 | 模型体积 | 压缩比 | 模型加载 (ms) | 文档向量化 (ms) | 向量化吞吐 (块/秒) | 写入 (ms) | 索引刷新 (ms) | 查询向量化 (ms) | seekdb 检索 (ms) | 端到端 (ms) | Recall@5 | HitRate@5 | nDCG@5 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 量化前基线 **FP32** | 94,851,877 B (90.46 MiB) | 1.000× | 1,647.40 | 6,759.57 | 5.33 | 688.65 | 472.22 | 18.22 | 32.52 | 102.12 | 0.7917 | 0.9286 | 0.7762 |
| **FP16** | 47,497,427 B (45.30 MiB) | **1.997×** | 1,150.75 | 3,449.94 | 10.43 | 412.49 | 345.45 | 12.00 | 16.78 | 54.79 | 0.7917 | 0.9286 | 0.7762 |
| **INT8 (`q8`)** | 24,010,842 B (22.90 MiB) | **3.950×** | **335.44** | **3,369.91** | **10.68** | 473.60 | 312.58 | **8.62** | 18.78 | **25.93** | **0.8274** | **0.9643** | **0.7900** |

### 4.1 体积与压缩比（纯权重口径，实测字节数）

| 精度 | 权重文件 | 字节数 | MiB | 压缩比（= FP32 ÷ 本项） |
|---|---|---|---|---|
| FP32 | `onnx/model.onnx` | 94,851,877 | 90.46 | 1.000× |
| FP16 | `onnx/model_fp16.onnx` | 47,497,427 | 45.30 | **1.997×** |
| INT8 | `onnx/model_quantized.onnx` | 24,010,842 | 22.90 | **3.950×** |

同口径另算「权重 + tokenizer/配置」总体积（各精度共用同一套 tokenizer/config，合计 440,333 B）：
FP32 95,292,210 B (90.88 MiB) / FP16 47,937,760 B (45.72 MiB) / INT8 24,451,175 B (23.32 MiB) → 压缩比 **1.988× / 3.897×**。
（`npm run models:info` 可复现这张表；`data/model-files.json` 记录了下载时的原始字节数。）

### 4.2 检索质量变化

| 对比 | ΔRecall@5 | ΔHitRate@5 | ΔnDCG@5 |
|---|---|---|---|
| FP32 → FP16 | 0.0000 | 0.0000 | 0.0000 |
| FP32 → INT8 | **+0.0357** | **+0.0357** | **+0.0138** |
| INT8 → FP32 | −0.0357 | −0.0357 | −0.0138 |

**如实解读**：
* 结论只能是「**在本次评测集上未观察到量化导致的检索质量下降**」；**不能**说 INT8 优于 FP32 —— 28 条查询的评测集上，一条查询的归属就会让 Recall@5 变化 0.036，与上表差异同量级。
* FP16 与 FP32 的三个指标完全一致，说明两者在本数据集上的排序结果基本相同（量化未改变语义排序的正常表现）。
* 评测方法：Recall@K = 命中的相关文档数 ÷ 相关文档总数（文档级，按 `metadata.doc_id` 把切块归并到源文档后，对 28 条查询取平均）；HitRate@K = 至少命中一条相关文档的查询占比；nDCG@K 用二值增益、DCG/IDCG 归一化。实现见 `scripts/verify.mjs` 阶段 8 与 `scripts/bench.mjs` 的 `runConfig(withQuality)`。
* **INT8 + WebGPU / INT8 + WASM 两行的浏览器端口径质量数据：未测**（原因见 §1）。

## 7. 复现方式

```bash
cd stepfun
npm run seekdb                 # 先确保数据库在跑
npm run bench                  # 主配置 → data/bench.json
npm run bench -- --all         # 追加 fp32 / fp16 / q8 精度对比
npm run bench -- --batch       # 追加 batch size 扫描
npm run bench -- --all --batch # 全量（本文所有数字的来源）
npm run bench -- --json        # 只输出 JSON
```

脚本会自动：拉起 seekdb（若未运行）→ 加载模型 → 切块 → 向量化 → 重建集合 → 批量写入 → 刷新索引 → 重复测量各阶段 → 写 `data/bench.json`。
所有计时均为**预热后**测量并取中位数；`--repeat` 可调整重复次数。
